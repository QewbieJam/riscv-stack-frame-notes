# RISC-V 函数序言三行代码的心智模型

> `addi sp, sp, -16` / `sd ra, 8(sp)` / `sd s0, 0(sp)`
>
> 这三行几乎出现在每一个非叶子函数的开头，但“`*(uint64_t *)(sp + 8) = ra` 到底写到哪块内存、往哪个方向长”这一点，非常容易想错。

本文把这三个问题讲清楚：

1. `sd ra, 8(sp)` 这条指令**有没有移动 `sp`**；
2. 它写的那 8 个字节**是从哪到哪**（向上还是向下数）；
3. 小端序在这里**影响什么、不影响什么**。

---

## TL;DR

```asm
addi sp, sp, -16      # sp = sp - 16
sd   ra, 8(sp)        # *(uint64_t *)(sp + 8) = ra
sd   s0, 0(sp)        # *(uint64_t *)(sp + 0) = s0
```

| 行 | 做什么 | `sp` 变了没 |
|---|---|---|
| ① `addi sp, sp, -16` | 栈指针下移到**低地址**，腾出 16 字节 | ✅ 变了（唯一改 `sp` 的一行） |
| ② `sd ra, 8(sp)` | 把 `ra` 的 8 字节复制到 `[sp+8, sp+16)`（帧的**高半区**） | ❌ 不变 |
| ③ `sd s0, 0(sp)` | 把 `s0` 的 8 字节复制到 `[sp+0, sp+8)`（帧的**低半区**） | ❌ 不变 |

**“小端序”只影响块内字节排列（低字节在低地址），不影响块的起始和延伸方向**——后者永远是从操作数里的那个地址开始、向高地址数 `sizeof` 个字节。

---

## 1. 指令拆解

```asm
sd   ra, 8(sp)          # *(uint64_t *)(sp + 8) = ra
```

| 部分 | 含义 |
|---|---|
| `sd` | **s**tore **d**oubleword：把 64 位寄存器值存到内存（RISC-V 里一个 doubleword = 8 字节） |
| `ra` | return address，返回地址寄存器（`x1`），存着函数返回后要跳回去的地址 |
| `8(sp)` | 内存操作数：基址寄存器 `sp` 加偏移 8，即地址 `sp + 8` |

`sd` 属于 `S` 型指令格式，机器码里编码的是 **`rs2`（源寄存器 `ra`）、`rs1`（基址寄存器 `sp`）、12 位有符号立即数 `8`**。注意这里有三个独立的角色，`sp` 只是“算地址用的基址”，不参与数据搬运。

## 2. 注释用 C 写出来是什么意思

```c
*(uint64_t *)(sp + 8) = ra;
```

这一行的语义分四步：

1. `sp + 8` —— 先算出地址值（栈指针 + 8 字节）；
2. `(uint64_t *)` —— 把这个地址值强制转换成“指向 `uint64_t`（64 位无符号整数）的指针”；
3. `*...` —— 解引用这个指针，得到那块内存；
4. `= ra` —— 把 `ra` 的内容（64 位）写进这块内存。

严格说 `(sp + 8)` 是“整数加整数再转指针”，`sp` 本身并不是指针类型。类型上更干净的等价写法：

```c
((uint64_t *)sp)[1] = ra;              // 下标 1 = 偏移 8
*(uint64_t *)((char *)sp + 8) = ra;    // 按字节偏移，最严谨
```

最后一种避免了“整数与指针相加”的歧义，也是编译器内部表示内存访问时常用的形式。

## 3. “那块内存”到底在哪：从起始地址向高地址数 8 字节

**向高地址方向（地址数值增大的方向）取 8 字节，范围是 `[A, A+8)`，其中 A 是指针的值。**

关键是不要把两件事搞混：

- **栈的增长方向**：RISC-V 的栈向**低地址**增长，所以 `sp+8` 的地址比 `sp` **高**；
- **一个对象的占用方向**：C 里的对象（这里是 `uint64_t`）总是从指针所指的那个字节开始，向**地址增大**的方向连续占 `sizeof` 个字节。

指针的值永远是对象**第一个字节（最低地址那个字节）**的地址，不存在“从指针向下延伸”的对象。

### 示意图

`p = (uint64_t *)(sp + 8)`，`*p` 覆盖的 8 个字节：

```
        地址（数值）
        ┌────────────┐
sp+16   │            │   ← 不属于 *p
        ├────────────┤
sp+15   │  byte 7    │  MSB（最高位字节）
sp+14   │  byte 6    │
        │    ...     │
sp+9    │  byte 1    │
sp+8    │  byte 0    │  LSB（最低位字节）← p 指向这里
        ├────────────┤
sp+7    │            │   ← 不属于 *p
        └────────────┘
        低地址
```

这 8 个字节的地址依次是 `sp+8, sp+9, …, sp+15`，也就是 **`sp+8` 到 `sp+15`，向高地址方向展开**。

### 和 `sd` 指令对得上

`sd ra, 8(sp)` 做的事情正好是：把 `ra` 的 64 位值按小端序拆成 8 个字节，写到 `[sp+8, sp+16)`：

- `ra` 的 bit 0–7（最低字节）→ 写到 `sp+8`
- `ra` 的 bit 56–63（最高字节）→ 写到 `sp+15`

这也就是为什么恢复时用 `ld ra, 8(sp)` 能原样读回来——同一个地址、同样的 8 字节、同样是向高地址展开。

## 4. 正确的三行心智模型

> ① `sp -= 16`，把栈帧下移到低地址；
> ② 把 `ra` 的 8 字节**复制**到 `[sp+8, sp+16)`（高半区），`sp` 不动；
> ③ 把 `s0` 的 8 字节**复制**到 `[sp+0, sp+8)`（低半区），`sp` 不动。

C 模型：

```c
sp = sp - 16;                    // ① 只有这一行改 sp
*(uint64_t *)(sp + 8) = ra;      // ② sp 不变，只是算了一次 sp+8
*(uint64_t *)(sp + 0) = s0;      // ③ sp 不变
```

`sp + 8` 只是**临时算出来的一个地址**，用完就丢，不写回。

## 5. 小端序只决定块内字节排列

假设 `ra = 0x0000_0000_0000_1042`：先算出地址 `[sp+8, sp+16)`，再把 8 字节从低地址到高地址依次填进去：

| 地址 | 值 | 说明 |
|---|---|---|
| `sp+8` | `0x42` | LSB，最低字节 |
| `sp+9` | `0x10` | |
| `sp+10` | `0x00` | |
| `sp+11` | `0x00` | |
| `sp+12` | `0x00` | |
| `sp+13` | `0x00` | |
| `sp+14` | `0x00` | |
| `sp+15` | `0x00` | MSB，最高字节 |

“小端”只回答“哪个字节放前面”这一个问题：**最低有效字节放在最低地址**。它**不**改变块的起点（永远是操作数里的那个地址），也**不**改变延伸方向（永远向高地址）。换成大端机器，同一块内存的字节顺序会反过来，但仍然是 `[sp+8, sp+16)` 这 8 个字节。

## 6. 四个常见误区

| # | 误区 | 事实 |
|---|---|---|
| 1 | `sd ra, 8(sp)` 会先把 `sp` 移动 8 字节 | ❌ 基址+偏移寻址**不写回**基址寄存器。ARM 的 `str x1, [sp, #8]!` 才会写回；RISC-V 没有 post-index/pre-index 写回。真正改 `sp` 的只有 `addi sp, sp, -16` |
| 2 | 写入是“从 `sp+8` 往下写到 `sp`” | ❌ 是 `[sp+8, sp+16)`，向**高地址**展开。若真的往回写，就会和 `sd s0, 0(sp)` 的 `[sp, sp+8)` 重叠，`s0` 会把 `ra` 踩掉 |
| 3 | `ra` 里装的就是这块栈内存 | ❌ `ra` 装的是**一个 64 位数值**（返回地址），它指向**代码段里的一条指令**，不是这块栈内存；`sd` 只是把这个数值复制一份到栈上 |
| 4 | 栈向低地址长，所以对象也向低地址展开 | ❌ 两件事无关。栈帧整体向低地址扩张，但帧内每个对象仍按 C 的对象模型向高地址展开 |

第 2 条还有一个很直接的“后果检验”：`s0` 在 `[sp+0, sp+8)`、`ra` 在 `[sp+8, sp+16)`，两块**互不重叠**，合计正好铺满 16 字节。这正是汇编器这样排布的原因。

## 7. 完整示例：递归 `sum_to`

```c
long sum_to(long n) { return n == 0 ? 0 : n + sum_to(n - 1); }
```

见 [`asm/sumto.s`](asm/sumto.s)：

```asm
sum_to:
    addi sp, sp, -16      # ① 开栈帧，sp 下移到低地址
    sd   ra, 8(sp)        # ② 保存返回地址，写 [sp+8, sp+16)
    sd   s0, 0(sp)        # ③ 保存 s0，写 [sp+0, sp+8)
    mv   s0, a0           # s0 = n（s0 能跨 call 存活）
    beqz a0, .Lbase       # n == 0 → 返回 0
    addi a0, a0, -1       # a0 = n - 1
    call sum_to           # a0 = sum_to(n-1)  ← 这行会改写 ra！
    add  a0, a0, s0       # a0 = n + sum_to(n-1)
.Lbase:
    ld   s0, 0(sp)        # ④ 恢复 s0
    ld   ra, 8(sp)        # ⑤ 恢复 ra
    addi sp, sp, 16       # ⑥ 收栈帧
    ret
```

### 为什么“必须”存 `ra`

`call` 是伪指令，展开后会把**返回地址写进 `ra`**。`sum_to(5)` 调用 `sum_to(4)` 时，`ra` 从“返回 `_start`”变成“返回 `sum_to` 内部”。如果不保存，`sum_to(5)` 结束时 `ret` 就会跳回自己内部，变成死循环。所以进函数先把 `ra` 存到栈上。

### 为什么用 `s0` 而不是 `t0`

- `s0`–`s11` 是 **callee-saved**：任何函数用完都会帮你还原；
- `t0`–`t6` 是 **caller-saved**：`call` 之后随便用，你原来的值就没了。

所以跨调用存活的 `n` 必须放进 `s0`（或者自己写到栈上）。

### 运行时栈帧（递归 3 层）

```
        高地址
        ┌──────────────────┐
        │  _start 的栈      │
        ├──────────────────┤ ← 初始 sp
  S-8   │ ra(→_start)      │
  S-16  │ s0(旧值)         │  ← sum_to(5) 的帧
        ├──────────────────┤ ← sp
  S-24  │ ra(→sum_to 内)   │
  S-32  │ s0(=5)           │  ← sum_to(4) 的帧
        ├──────────────────┤ ← sp
  S-40  │ ra(→sum_to 内)   │
  S-48  │ s0(=4)           │  ← sum_to(3) 的帧
        └──────────────────┘ ← sp
        低地址
```

每层各占 16 字节，`s0` 在低半区、`ra` 在高半区，两条 `sd` 正好把一帧填满。逐层 `ret` 时再一层层弹回去。

## 8. 编译器对照（`gcc -O1 -S`）

```asm
sum_to:
	addi	sp,sp,-16        # ← 一模一样的序言
	sd	ra,8(sp)
	sd	s0,0(sp)
	mv	s0,a0
	bne	a0,zero,.L4
.L2:
	mv	a0,s0
	ld	ra,8(sp)
	ld	s0,0(sp)
	addi	sp,sp,16
	jr	ra
.L4:
	addi	a0,a0,-1
	call	sum_to
	add	s0,s0,a0
	j	.L2
```

序言和尾声与手写版**逐条相同**，只是把两条返回路径合并成 `.L2` 一个出口。

### 对照：叶子函数不需要栈帧

```c
long add3(long a, long b, long c) { return a + b + c; }
```

```asm
add3:
    add a0, a0, a1
    add a0, a0, a2
    ret
```

没有 `call`，`ra` 不会被覆盖，也没有需要跨调用保存的变量——**零序言、零尾声、零栈帧**。是否开栈帧取决于“体内有没有 `call`、有没有需要跨调用存活的变量”，跟函数大小无关。

## 9. 实验复现

需要 `riscv64-linux-gnu-gcc` 和 `qemu-riscv64`：

```bash
cd asm
riscv64-linux-gnu-gcc -march=rv64gc -mabi=lp64 -nostdlib -static -o sumto sumto.s
qemu-riscv64 ./sumto; echo "exit code = $?"     # 期望 15，即 sum_to(5)=15
```

`_start` 里 `li a0, 5` 后调用 `sum_to`，再用 `exit` 系统调用（`a7=93`）把结果作为退出码返回，所以 `$?` 就是 `sum_to(5)`。

## 10. 速查

- `sd` / `ld` 里 `imm(rs1)` 的含义：**地址 = rs1 + imm**，`rs1` 不被修改。
- 一个 64 位对象的范围：`[addr, addr+8)`，从 `addr` 起**向高地址**。
- 小端序：最低有效字节放**最低地址**。
- 栈：向**低地址**增长；帧内对象：各自向**高地址**展开。
- 只有改 `sp` 的指令才能动栈指针；`sd`/`ld` 不会。
